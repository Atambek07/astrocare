# Data Provenance and Lineage

**Version:** 2026-11-15  
**Purpose:** ensure that every scientific or simulated value can be traced to its origin, transformation or generator.

---

## 1. Provenance classes

| Class | Definition | Required evidence |
| --- | --- | --- |
| `NASA_REAL` | Actual NASA/OSDR measurement or metadata. | Study, file, source URL, original value/unit, subject/timepoint where available. |
| `NASA_DERIVED` | Calculation or transformation over NASA data. | Parent records, transformation method, processing version, limitations. |
| `SYNTHETIC` | Value generated by the simulation engine. | Engine version, model version, seed, scenario, profile and generation metadata. |

A value is never promoted between classes.

---

## 2. Provenance schema

The shared provenance model includes:

- `provenance_id`;
- `source_type`;
- `nasa_study_id`;
- `nasa_dataset_id`;
- `source_file`;
- `source_url`;
- `publication_reference`;
- `subject_id`;
- `collection_timepoint`;
- `measurement_timestamp`;
- `measurement_unit`;
- `original_value`;
- `normalized_value`;
- `processing_method`;
- `quality_status`;
- `metric_key`;
- `fallback_status`;
- `derived_from`;
- `source_verified_utc`;
- `notes`.

Additional fields preserve original and normalized units, processing version, checksum, download/processing timestamps, license/access terms and synthetic generator metadata.

## 3. NASA_REAL lineage example

```text
OSD-569 public study page
  ↓
LSDS-7 Complete Blood Count CSV
  ↓
SHA-256 and download manifest
  ↓
Original analyte, value and unit
  ↓
Normalized value and quality status
  ↓
NASA_REAL provenance record
```

Example field mapping:

| Field | Example |
| --- | --- |
| Study | `OSD-569` |
| File | `LSDS-7_Complete_Blood_Count_CBC.upload_SUBMITTED.csv` |
| Original value | `13.8` |
| Original unit | `g/dL` |
| Normalized value | `13.8` |
| Timepoint | `L-92` |
| Source class | `NASA_REAL` |

Absolute measurement time is not fabricated when the source supplies only a relative timepoint.

## 4. NASA_DERIVED lineage example

```text
OSD-572 MetaPhlAn species table
  ↓
Species-level relative abundances
  ↓
Shannon diversity calculation
  ↓
NASA_DERIVED record with method and parent file
```

Method:

```text
H = -Σ p_i ln(p_i)
```

where `p_i` is the relative abundance of species `i`.

## 5. SYNTHETIC lineage example

```text
AstroCare simulation configuration
  ↓
Astronaut profile and seed
  ↓
Hybrid physiological integration
  ↓
StreamTick / DailyTelemetryLog
  ↓
SYNTHETIC provenance ID
```

Required synthetic metadata:

- engine version;
- model version;
- random seed;
- scenario ID;
- parameter profile;
- mission timestamp;
- generation timestamp.

---

## 6. Checksum and file lineage

Every selected NASA download records:

- study ID;
- file name;
- source URL;
- expected and actual size;
- SHA-256;
- local path;
- retrieval timestamp;
- access/redistribution status.

This connects processed values back to a byte-level source artifact.

---

## 7. Transformation history

Each processed value includes:

- `processing_method`;
- `processing_version`;
- `pipeline_version`;
- source file SHA-256 where available;
- limitations.

Examples:

- `identity` for a preserved measurement;
- `shannon_diversity_from_species_relative_abundance`;
- `descriptive summary by study/panel/analyte/timepoint/unit`;
- simulation generation method for synthetic telemetry.

---

## 8. Presentation rules

The frontend separates:

1. NASA evidence in **Data Sources**.
2. Synthetic live telemetry from the simulation.
3. Explicit demo/mock mode when the backend is unavailable.

A NASA laboratory value is never displayed as a live vital sign.

---

## 9. Limitations

1. Some OSDR values lack absolute timestamps.
2. Some analyte units are source-specific and remain unconverted.
3. NASA data are sparse and cannot establish individual continuous baselines.
4. Simulation parameters informed by NASA evidence remain engineering assumptions unless independently calibrated.
