# Local AI Model

**Status:** implemented feature  
**Scope:** AI Assistant chat model selection  
**Decision-support status:** the local model provides decision support only. It is not a diagnosis, treatment recommendation, or medically validated system.

---

## 1. Summary

AstroCare can optionally use a local Ollama model for AI Assistant questions. The complete site works without Ollama: if no local model is available, the AI Assistant continues to use the built-in rule-based answers.

The user selects the model in the **AI Assistant** view. The selection is stored locally in the browser and is not synchronized between devices.

---

## 2. User-facing behavior

### With a local model available

If the backend and Ollama are reachable and at least one non-embedding model is installed, the AI Assistant shows a **Local AI model** block containing:

1. `Built-in answers (no AI)`;
2. every installed local model that is exposed by the backend.

Embedding models are hidden.

### Without a local model

If the backend is unreachable, Ollama is unavailable, or no eligible model is installed, the block shows:

```text
No local model available — using built-in answers.
```

It also provides a **Check again** button. Built-in rule-based answers continue to work.

---

## 3. Selection persistence

The selected model is stored in browser `localStorage` under:

```text
astrocare.aiModel
```

If a remembered model is no longer installed, AstroCare treats it as unavailable and falls back to built-in answers.

---

## 4. Question flow

1. AstroCare first computes the built-in rule-based answer using `answer()` in `frontend/src/lib/astroAI.ts`.
2. If a local model is selected, the question is sent to `POST /ask` with that model.
3. The UI shows `Local AI is thinking…` while waiting.
4. The UI request timeout is 45 seconds.
5. If the model answers successfully, its text replaces the first message of the built-in answer.
6. The model response is labeled:
   - `Local AI model · decision support only`.
7. Protocol steps, body-zone links, and action buttons from the built-in answer are retained.
8. If the backend is down, the request times out, or the response source is not `llm`, AstroCare silently keeps the built-in answer. No error is shown to the user.

---

## 5. Backend API

### `GET /models`

Returns available local models.

```json
{
  "available": true,
  "models": ["qwen2.5:7b-instruct"],
  "default": "qwen2.5:7b-instruct"
}
```

When Ollama is unreachable:

```json
{
  "available": false,
  "models": [],
  "default": null
}
```

Model names containing `embed` are excluded.

### `POST /ask`

The request now accepts an optional `model` field:

```json
{
  "astronaut_id": "astro-01",
  "question": "What should the crew monitor next?",
  "model": "qwen2.5:3b-instruct"
}
```

Rules:

- `astronaut_id` must refer to an existing backend astronaut ID; backend IDs use lowercase names such as `astro-01`, and other casing returns `404`;
- `model` must match `[A-Za-z0-9._:/-]{1,100}`;
- invalid names return `400 {"error": "invalid model name"}`;
- without `model`, the previous `/ask` behavior applies.

The response shape is unchanged:

```json
{
  "answer": "...",
  "source": "llm",
  "disclaimer": "...",
  "contextTimestamp": "..."
}
```

On failure, `source` is `fallback`.

## 6. Environment variables

| Variable | Effect |
| --- | --- |
| `ASTRO_DOCTOR_OFFLINE=1` | Disables the background recommendation layer. It does **not** block an explicitly selected chat model in `/ask`. |
| `ASTRO_OLLAMA_URL` | Configures the Ollama base URL used by the Doctor Layer and chat request. |
| `ASTRO_OLLAMA_MODEL` | Configures the default/background recommendation model. It does not override a user-selected chat model. |

## 7. Prompt design

The `/ask` prompt was rewritten in `backend/src/astro_brain/doctor/prompts.py` using:

- `ASK_SYSTEM_PROMPT`; and
- `build_ask_prompt`.

The prompt is intentionally short and constrained. It includes one example, asks for concise output, refuses non-health requests, and does not send `likelyConditions` to the model.

Backend status data passed to the model includes:

- `alertLevel`;
- `news2Score`;
- `activeFlags`;
- `flagDetails`;
- `doctorRecommendation`;
- plan status.

Frontend-only values, such as the displayed cabin CO₂ and sleep fields generated by the demo frontend, are not sent to the model.

---

## 8. Verification and limitations

AstroCare was verified with `qwen2.5:7b-instruct` only.

Smaller models such as 1.5B and 3B variants were **not** tested with the new prompt. Documentation should not recommend them as verified options.

Known limitations:

1. The local model is decision support, not a diagnosis tool.
2. It may invent values that are not present in backend data.
3. It sees backend status data only, not frontend-only cabin CO₂ or sleep display data.
4. The AI Assistant UI waits up to 45 seconds for a response.
5. Inference can be slow on weak laptop hardware.
6. There are no new automated tests for `GET /models` or the `model` field in `/ask`.
7. Prompt behavior was checked manually, not through a formal benchmark.
